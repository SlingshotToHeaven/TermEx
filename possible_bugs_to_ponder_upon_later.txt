# Possible Architectural Edge Cases and Bugs in TermEx (To Ponder Upon Later)

This document catalogs potential edge cases, limitations, and architectural failure modes in TermEx resulting from the design choice of using userspace dynamic interposition (LD_PRELOAD + libc wrapping) and dynamic path redirection instead of kernel-level filesystem namespaces.

---

### 1. Mixed Libc Ecosystems (Android Bionic vs. glibc / musl) [RESOLVED - Phase 1]
- **Problem**: Termux packages use Android Bionic libc (`libc.so`), but glibc environments (`glibc-repo`, `agy`, desktop environments, Box64/FEX) run under GNU libc (`ld-linux-aarch64.so.1` + `libc.so.6`).
- **Symptom**: `LD_PRELOAD` is inherited across `execve()`. When a Bionic process spawns a glibc binary, glibc attempts to load `libtermex-redirect.so`. Because the redirect library depends on Bionic (`libdl.so`, `libc.so`), glibc fails to resolve `libdl.so` in its search paths and terminates with `Permission denied` or crashes due to ABI incompatibilities.
- **Resolution**: Implemented ELF PT_INTERP program header parsing (`check_is_glibc_binary()`) and isolated `LD_PRELOAD` in `ensure_env()`. Automatically strips `libtermex-redirect.so` from `LD_PRELOAD` whenever spawning glibc dynamic linkers or binaries.

---

### 2. Direct Linux Syscalls Bypassing Libc (`asm volatile("svc 0")`)
- **Problem**: `LD_PRELOAD` only intercepts calls to dynamically linked C library functions (`open`, `stat`, `execve`). Any program invoking kernel syscalls directly without going through `libc.so` completely bypasses `libtermex-redirect.so`.
- **Affected Programs**:
  - **Go binaries compiled with `CGO_ENABLED=0`**: Pure Go uses its own assembly syscall routines for filesystem access. If a Go binary has hardcoded paths pointing to `/data/data/com.termux/...`, it will make raw syscalls to the kernel and fail.
  - **Rust / Zig / Assembler programs** that use direct syscall implementations or their own raw syscall backends instead of libc bindings.

---

### 3. Statically Linked Binaries (`-static`)
- **Problem**: Statically linked ELF binaries do not load a dynamic linker (`/system/bin/linker64` or `ld-linux.so`). The Linux kernel loads and starts the executable directly without reading or honoring `LD_PRELOAD`.
- **Symptom**: `libtermex-redirect.so` is never injected into statically linked processes. Any hardcoded paths within static binaries remain unredirected.

---

### 4. Kernel ELF Interpreter Loading (`PT_INTERP`) [RESOLVED - Phase 1]
- **Problem**: When `execve()` executes a dynamically linked ELF binary, the Linux kernel (not userspace) parses the binary's `PT_INTERP` header and loads the interpreter.
- **Symptom**: If an ELF binary specifies `PT_INTERP = /data/data/com.termux/files/usr/glibc/lib/ld-linux-aarch64.so.1`, on secondary users (e.g., User 10) or on TermEx where `/data/data/com.termux` does not exist or has restrictive permissions, the kernel itself cannot access `/data/data/com.termux` (`EACCES` or `ENOENT`). The execve call fails with `Permission denied` before userspace can run.
- **Resolution**: In `handle_shebang_exec()`, inspected ELF headers for `PT_INTERP` pointing to `ld-linux`. When detected, rewritten the execution into a direct invocation of the redirected dynamic linker: `[redirected_ld_linux, "--library-path", glibc_lib_dir, target_binary, ...args]`. Verified direct execution of glibc binaries across subshells and PATH lookups.

---

### 5. `LD_PRELOAD` Sanitization by Tools and Environment Strippers [RESOLVED - Phase 2]
- **Problem**: Programs or scripts that clean their environment (e.g., `env -i`, `sudo`, `login`, custom daemons, or certain Python/Node runner scripts) remove `LD_PRELOAD` and `LD_LIBRARY_PATH`.
- **Symptom**: Subprocesses spawned from these scripts lose the interposition library and dynamic library search path. Bionic executables with hardcoded runpaths fail with `CANNOT LINK EXECUTABLE ... library "libandroid-support.so" not found`.
- **Resolution**: Enhanced `ensure_env()` to automatically reinject both `LD_PRELOAD` and fallback `LD_LIBRARY_PATH` (`$PREFIX/lib`) whenever an execution occurs with a stripped environment (e.g. `env -i`). Verified clean execution of bash, coreutils, tar, gzip, curl, and glibc binaries under `env -i`.

---

### 6. Android System Binaries and Linker Restrictions [RESOLVED - Phase 3]
- **Problem**: When a script invokes Android system tools (e.g., `/system/bin/sh`, `/system/bin/am`, `/system/bin/pm`, `app_process`), Android's linker enforces strict namespace and security restrictions.
- **Symptom**: In modern Android versions, the linker refuses to load non-system libraries from `LD_PRELOAD` into system binaries, printing linker warnings (`WARNING: linker: could not load library ...`) to stderr, which can break scripts that parse stdout/stderr cleanly. Furthermore, inheriting app `LD_LIBRARY_PATH` can cause system utilities to accidentally link incompatible app libraries.
- **Resolution**: Implemented `is_system_binary()` to identify executions of `/system/`, `/apex/`, `/vendor/`, `/product/`, `/system_ext/`, and `/odm/` binaries. In `ensure_env()` and `handle_shebang_exec()`, automatically strip both `libtermex-redirect.so` from `LD_PRELOAD` and `LD_LIBRARY_PATH` when spawning Android system binaries, guaranteeing zero linker pollution or warnings.

---

### 7. File Descriptor and Pseudofilesystem Leaks (`/proc/self/*`) [RESOLVED - Phase 4]
- **Problem**: Utilities that inspect process identity via `/proc` (e.g. `readlink("/proc/self/exe")`, `realpath("/proc/self/exe")`, `/proc/self/cmdline`) would observe the real path (`/data/user/<userId>/com.termex/...`) and the real package name (`com.termex`).
- **Symptom**: Any script or package that validates its environment by asserting that `/proc/self/exe` contains `com.termux` or that its package name is strictly `com.termux` will detect the mismatch and fail or abort.
- **Resolution**: Implemented `virtualize_returned_path()` in `termex-redirect.c` for `readlink()`, `readlinkat()`, `__readlink_chk()`, `__readlinkat_chk()`, and `realpath()`. Whenever queries target `/proc/`, any resolved path starting with the active app directory (`/data/user/<userId>/com.termex`) is transparently rewritten back to the canonical upstream path (`/data/data/com.termux`). Verified with native C test binaries and coreutils `readlink`/`realpath`.

---

### 8. Termux Add-on Plugins & Android IPC (Termux:API, Termux:GUI, Termux:Widget)
- **Problem**: Add-on APKs use Android Intents, Broadcasts, and Content Providers explicitly bound to `com.termux` package name and signed permissions (`com.termux.permission.RUN_COMMAND`).
- **Symptom**: Standard third-party plugins installed from F-Droid or Play Store target `com.termux` and will not communicate with `com.termex` unless also recompiled or patched with the matching package name and signature.

---

### 9. Hardcoded Path Sizes in Precompiled Buffers [AUDITED & MITIGATED - Phase 5]
- **Problem**: The string `/data/data/com.termux` is 21 characters. On secondary Android users, the path is `/data/user/10/com.termex` (23 characters) or longer for multi-digit user IDs (`/data/user/100/...`).
- **Symptom**: If an upstream C/C++ program allocates a fixed-size buffer exactly sized for `strlen("/data/data/com.termux/...")` or uses `PATH_MAX` assumptions that don't account for path expansions, buffer overruns or string truncations could theoretically occur.
- **Audit & Mitigation**:
  - Audited all internal interception wrappers in `termex-redirect.c`: all temporary stack buffers (`tbuf`, `buf`, `interp_buf`, `new_path`) are consistently allocated to 1024 or 4096 bytes with strict `snprintf(buffer, bufsize, ...)` bounds checking.
  - In `virtualize_returned_path()`, bounded path copying protects caller buffers (`to_copy = min(n, bufsiz)`).
  - In `handle_shebang_exec()`, dynamic array allocation (`malloc((argc + 4) * sizeof(char*))`) guarantees zero stack overflow regardless of command length.
  - In `ensure_env()`, expanded combined preload buffer to 2048 bytes and dynamic environment arrays allocate exact capacity based on variable count.
